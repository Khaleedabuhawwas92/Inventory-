# نظام إدارة المخزون — تطبيق سطح المكتب (Electron)

غلاف Electron حول نفس الواجهة الأمامية (`frontend`)، يتصل بخادم (`backend`) **خارجي ومستقل** — لا يقوم Electron بتشغيل أو إدارة الخادم بأي شكل؛ فقط يفتح نافذة تعرض الواجهة وتتصل بالخادم عبر HTTP، تماماً كما تفعل نسخة الويب.

## كيف يعمل

- **وضع التطوير (`npm run dev`)**: أمر واحد يقوم بـ: تشغيل خادم Vite للواجهة الأمامية، الانتظار حتى يصبح جاهزاً، ثم تشغيل Electron الذي يفتح نافذة تشير إلى `http://localhost:5173`. لا حاجة لفتح أكثر من نافذة طرفية واحدة.
- **وضع الإنتاج (المُعبّأ)**: النافذة تحمّل ملفات الواجهة المبنية مباشرة من القرص عبر `BrowserWindow.loadFile(...)` — **لا يعتمد على أي خادم Vite أو رابط `localhost:5173`**. عنوان الخادم (Backend API) يُقرأ من إعداد قابل للتغيير (انظر أدناه)، وليس مكتوباً بشكل ثابت داخل الحزمة.

## عنوان الخادم (Backend API) — قابل للإعداد دائماً

يُحل عنوان الخادم بالترتيب التالي:
1. متغير البيئة `API_BASE_URL` (لأغراض التطوير/التخصيص المتقدم).
2. ملف `config.json` داخل مجلد بيانات المستخدم الخاص بالتطبيق (`app.getPath('userData')` — عادة `%APPDATA%/inventory-system-desktop/config.json` على ويندوز). يُنشئه التطبيق تلقائياً بالقيمة الافتراضية عند أول تشغيل إن لم يكن موجوداً، بحيث يمكن لأي مسؤول تعديله لاحقاً (توجيه التطبيق نحو خادم آخر) **دون الحاجة لإعادة بناء التطبيق**.
3. القيمة الافتراضية الثابتة: `http://localhost:5000/api`.

## التوجيه (Routing) داخل Electron

الواجهة تستخدم **hash routing** (`#/dashboard`) فقط عند التشغيل داخل Electron (يُكتشف تلقائياً عبر `window.desktopApp.isElectron`)، بينما تبقى نسخة الويب على history mode بروابط نظيفة (`/dashboard`) دون أي تغيير. السبب: عند تحميل الملفات عبر `file://`، تحديث الصفحة (refresh) على مسار history-mode حقيقي (مثل `file:///.../dashboard`) يفشل لأنه لا يوجد ملف بهذا الاسم فعلياً؛ hash routing يتجنب هذه المشكلة جذرياً لأن التنقل بين الصفحات لا يغيّر الملف المطلوب فعلياً (يبقى دائماً `index.html`).

لنفس السبب، بناء الواجهة لـ Electron يستخدم مسارات أصول (assets) **نسبية** (`./assets/...`) بدل المطلقة (`/assets/...`) — عبر بناء منفصل (`frontend/dist-electron`، الأمر `npm run build:frontend:electron`)، مختلف عن بناء الويب العادي (`frontend/dist`) الذي يبقى كما هو دون أي تغيير.

## الأمان

- `contextIsolation: true`
- `nodeIntegration: false`
- `sandbox: true`
- لا استخدام لوحدة `remote` إطلاقاً.
- `preload.js` يُعرّض فقط واجهة API محدودة وآمنة (`window.desktopApp`) عبر `contextBridge`.
- الروابط الخارجية (`target=_blank`، أو أي تنقّل خارج نطاق التطبيق) تُفتح في متصفح المستخدم الافتراضي عبر `shell.openExternal`، ولا تُفتح أبداً داخل نافذة التطبيق نفسها.

## التطوير (Dev)

```bash
cd desktop
npm install      # مرة واحدة فقط
npm run dev
```

هذا الأمر الوحيد يكفي: يشغّل Vite وElectron معاً في نافذة طرفية واحدة (عبر `concurrently` + `wait-on`)، ويغلق كليهما معاً عند إغلاق أي منهما. يجب تشغيل الخادم (`backend`) بشكل منفصل كالمعتاد (`cd backend && npm run dev`) — يبقى خارجياً دائماً، في التطوير كما في الإنتاج.

## البناء للإنتاج (Production Build)

```bash
cd desktop
npm install
npm run build
```

هذا الأمر يقوم بالترتيب بـ:
1. بناء نسخة الويب العادية (`frontend/dist`) — دون تغيير.
2. بناء نسخة مخصصة لـ Electron (`frontend/dist-electron` — مسارات أصول نسبية).
3. تعبئة `electron-builder`، مع نسخ `frontend/dist-electron` فقط كمورد إضافي (`extraResources`) داخل الحزمة — **لا يتم تضمين `backend` في الحزمة إطلاقاً**، فهو خدمة خارجية دائماً.

الناتج يظهر في `desktop/release/` (مثال: `release/نظام إدارة المخزون Setup 1.0.0.exe` على ويندوز).

### تشغيل الخادم مع النسخة المُعبأة

التطبيق المُعبأ **لا يحتوي على خادم أو MongoDB مدمجَين**. شغّل `backend` بشكل مستقل (محلياً أو على خادم بعيد)، ثم:
- إن كان يعمل على `http://localhost:5000` (الافتراضي)، لا حاجة لأي إعداد إضافي.
- وإلا، عدّل `apiBaseUrl` في ملف `config.json` (انظر أعلاه) ليشير إلى العنوان الصحيح، ثم أعد تشغيل التطبيق.

### الأيقونة

الملف `build/icon.png` **غير موجود بعد** — البناء الحالي يستخدم أيقونة Electron الافتراضية (لا يفشل البناء، فقط تحذير). قبل التوزيع النهائي، أضف أيقونة حقيقية:
- Windows: `build/icon.ico`
- macOS: `build/icon.icns`
- Linux: `build/icon.png` (256×256 أو أكبر)
